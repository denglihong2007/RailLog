# 经由线路在平行线间横跳

*迁移自 Claude Code 项目记忆 · 更新于 2026-10-11*

2026-10-11 排查「D26 青岛北→大明湖 在 胶济线 / 胶济客专线 之间反复横跳」。**不是选错线，是平局随意打破**。

根因在数据：`routes.db` 里这两条线在共享站的里程桩**完全相同**（济南 0 / 大明湖 3 / 淄博 110 /
昌乐 186 / 潍坊 210 / 高密 295 / 即墨 351 / 城阳 362 / 青岛北 378 / 青岛 393），只在中间站上不同
（胶济线 蓝村 341·胶州 320·芝兰庄 308、黄台 7·金岭镇 123·东风 127·临淄 132；客专 胶州北 330、
五里堂所 32·章丘 49·青州市 153）。于是每一对相邻站都有两条**长度一模一样**的路径。

触发链：`resolveJourney` 对**每一对相邻站**独立搜一次 → 目标里程恰好等于最短距离 → 误差 0 ≤
`_distanceTolerance`(0.55) → `_distanceMatchingOrClosestPath` 早退、直接交回 Dijkstra 最短路径 →
**带线路条数惩罚的优先级搜索（唯一会偏好「少换线」的那段）根本没跑** → Dijkstra 并列判定写的是
`nextDistance >= ...` 就跳过（先松弛者赢），等长平行线由「谁的中间站先被弹出」决定，逐段翻。

复现（把 `_RouteGraph.fromRows` + `_shortestPath` 照抄成 Python，跑 `app/assets/db/routes.db`）：
`青岛北→潍坊` 一整段就产出 胶济线(27) / 胶济客专线(56) / 胶济线(85)，与库里存的 ViaRoutes 一字不差；
即墨、高密两个翻转点都在**同一段内部**。反例佐证：整段搜 `青岛北→济南` 时最短路径其实是 349km 的
济青高速线，于是走约束搜索、优先单一名 → 干净的 `胶济线 青岛北→济南 378`（库里也有这条记录）。

**Why:** 横跳只是表象，UI 上表现为 5 段来历，贴轨再按「线路名|起|终」查折线，地图就在两条平行走廊间来回跳。

**How to apply:** 再遇到「某段在两条平行线之间来回换名」，先比共享站的里程桩
（`SELECT station_name, mileage FROM stations WHERE route_version_id IN (…) ORDER BY …`）；相同就是这个坑。
与 [misrouted-alignment-causes](./misrouted-alignment-causes.md) 那三个离线线位病是两回事（那是 OSM 几何选错，这是 App 侧名字选中谁）。

**2026-10-11 已修（走的是「平局规则」那条路）**：`_shortestPath` 改成状态 = 「站 + 到达时用的
线路名」、代价按 `[里程, 换线次数]` 字典序比（`_MinHeap` 的优先级随之从 double 改成 `List<double>`
+ `_comparePriority`）；`_resolveJourney` 把上一段的线路名作为 `initialRouteName` 传给下一段，
从它接着走不算换线。回归测试 `app/test/route_service_test.dart`（照抄 trip_map_service_test 的
sqflite-ffi + path_provider mock，能读真实 routes.db）：改前整段搜输出 `[胶济线, 胶济客专线, 胶济线]`、
逐段搜输出 `[胶济线, 胶济客专线, 胶济线, 胶济客专线, 胶济线]`（与库里存的 ViaRoutes 逐字相同），改后都是单段 378km。

**2026-10-11 又修一轮（1461/1462 丹阳→常州 走了沪宁高速线）**：时刻表的累计里程和 routes.db 的
里程桩不是同一套刻度，沪宁段每过一个站就差 1 km（南京→常州 时刻表 137，两条线的里程桩都是 136）。
约束搜索 `_distanceMatchingOrClosestPath` 只认「误差更小者胜」，于是借道走法
京沪线 南京→丹阳 92 + 沪宁高速线 丹阳→常州 45 = 137（误差 0）压过了纯 京沪线 136（误差 1 >
`_distanceTolerance` 0.55）。改法（用户选的「对算法」）：加 `_distanceTieBand = 1.0`，接受门槛
放宽到 `_distanceMatchTolerance = 0.55 + 1.0`，命中里取「用到的线路名最少」的走法；优先级从加权和
`线路数 * band + 里程 + 下界` 改成真字典序 `[线路数, 里程 + 下界]`（加权和在下界大的时候会让线路多
的插队，而并列取舍正靠这个次序）；剪枝窗口下限抬到并列带宽度，否则窗口收窄到 0 误差时会把「多 1 km
但不换线」的候选剪掉。顺带把 `initialRouteName` 也接进了约束搜索（起点状态的 usedRouteNames 预置
上一段的线路名），即下面记的口子①。

**留下的口子**：①已闭（2026-10-11）；②现在只保证「同一条线」，选中的是哪一条仍由 routes.db 行序/
上一段延续决定：单段搜（没有上一段）南京→常州 仍是两条线等里程的硬并列，落到沪宁高速线，要分清
必须让源数据的里程桩区分开。回归测试在 `app/test/route_service_test.dart` 第二组（1461 → `济南线
济南→党家庄 15 + 京沪线 党家庄→上海 953`；1462 → 单段 `京沪线 苏州→南京 217`）。

**2026-10-11 第三轮（D966 成都东→北京丰台 在太原枢纽插了一段 石太客专线）**：并列带放宽接受窗口
以后暴露的新病——**排序判据的第二位原来是「潜力里程」（本节点累计里程 + 到终点的最短距离下界），
不是离目标的误差**。于是「为了凑够目标里程在枢纽里反复换线」的走法潜力更小、先出队，被并列带当场
收下；真正贴着目标的那条反而没轮到。D966 的 西安北→石家庄 目标 807（时刻表累计里程，比 routes.db
的轴大 3 km）：病态走法 `徐兰高速线 33 + 大西临潼东联络线 5 + 大西高铁 湾李所→长风街所 540 +
石太客专线 长风街所→太原 4 + 大西高铁 太原→太原东 3 + 石太客专线 太原东→石家庄 221 = 806`（误差 1）
压过了 `… + 大西高铁 湾李所→太原东 548 + 石太客专线 太原东→石家庄 221 = 807`（误差 0）。改法：
优先级改成 `[线路名数, 离目标的误差下界, 潜力里程]` 三位字典序，终点节点第二位直接用真误差
（`edge.toStation == end ? (d - target).abs() : max(0, d + lowerBound - target)`，见 `_errorLowerBound`）。
这样「先出队的就是线路名最少的贴目标走法」，并列带只负责放宽「线路名少一个可以多 1 km 误差」。

太原枢纽的数据背景（三线共享四站、里程桩不一致，这是病根）：
大西高铁 `太原东 248 / 太原 251 / 长风街所 256 / 太原南 260`（轴是 怀仁东 0 → 西安北 831）、
石太客专线 `太原东 221 / 太原 224 / 长风街所 228 / 太原南 232`（轴是 石家庄 0）、
郑太客专 `太原南 428 / 长风街所 432`。所以「长风街所→太原」在大西是 5 km、在石太是 4 km，
靠 大西→石太→大西→石太 反复换名能多凑几公里。回归测试在 `app/test/route_service_test.dart`
第三组「不为了凑里程在枢纽里反复换线」（断言「每条线路只出现一段」，旧次序下必挂）。

**2026-10-11 第四轮（D16 甘泉北→延安 换上平行的 包西高铁延西段）**：`_distanceTieBand` 固定 1 km
的错——**刻度差是逐站累积的**，走法越长差得越多，固定带宽等于「长走法误差稍大就被判成不贴目标，
短走法插一段平行线反而贴」。D16 的 西安东→延安 目标 328：老实走 西康线 + 陇海线(宁西线西合段) +
包西线 是 331（15 站，误差 3），而在 甘泉北 换 包西高铁延西段（34 km，包西线 上是 40 km）凑出
327（误差 1）。改法：`_mileageTieBand(hops) = max(_distanceTieBand, _mileageDriftPerHop 0.5 * hops)`、
`_matchTolerance(hops) = _distanceTolerance + _mileageTieBand(hops)`（取代按站数固定 1 km 的旧常量），
`_ExactSearchNode` 加 `hopCount`；剪枝窗口下限也随当前站数放宽。

**同轮暴露的第二个坑**：带宽一放宽，「终点节点是第一个出队的」不再等于「它就是该线路名数下最贴目标的
那个」——**中转节点用的是误差下界，终点用真误差，两者可以在同一中转站上打平**（新丰镇→西安 有
陇海线 27+10 与 宁西线西合段 35 两条等长走法，前者合 328 = 时刻表值、后者合 326，谁先弹出全看堆内次序）。
改法：不再「首个可接受终点即返回」，改成先收下候选（`accepted`/`acceptedNames`/`acceptedError`），
继续把「线路名数不多于它、误差下界还小于它」的节点走完（`_MinHeap.peekPriority`），收尾时取真误差最小的。

**这轮顺带发现的数据事实**（别当 bug 再查一遍）：`陇海线` 与 `宁西线西合段` 在 新丰镇→西安 完全并行
（新丰镇 35 / 窑村 17 / 灞桥 10 / 西安 0，两边都是 35 km），走哪条是**无解的硬并列**，测试只能对
「折返拆成两段 + 总里程 473」断言，不能锁死线路名。另外 D966 的 西安北→石家庄 正解从 807（4 段，
含 大西临潼东联络线 那段凑里程的借道）变成 **804（2 段）**——旧期望值本身就是「借道凑里程」的产物，
所以改测试期望时要连带这段理由写进注释。回归测试：第二组 1461/1462 与第四组「刻度差随经过站数累积」，
D16 那条断言「3 段、末段是 包西线、到 延安、合计 331、不含 包西高铁延西段」。
